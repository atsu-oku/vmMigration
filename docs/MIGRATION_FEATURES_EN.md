# Staged-to-Production Migration Enhancements

This document summarizes the recent enhancements made to the staged-to-production migration workflow. The goal is to help engineers understand how guest configuration updates, command tracking, and firewall synchronization now operate when running `cloneAndVmotion.py`.

## Command Execution Logging
- Every guest command issued through `guest_commands.py` is captured before execution and forwarded to `cloneAndVmotion.py` via `set_command_logger(register_command_execution)`.
- The helper `register_command_execution` stores both the raw command and a short Japanese description in `COMMAND_EXECUTION_LOG`. Descriptions are auto-generated by `_describe_command`, but you can supply a clearer string beforehand with `remember_command_description(command, description)`.
- `_print_execution_summary()` prints commands in chronological order at the end of the run, alongside the existing success and failure sections. Each entry shows the description first, then the exact shell command for easy replay.
- When `find_and_extract.sh` is used during STG->PRD prep, its `transform` subcommand now emits structured change logs under `/tmp/<user>/find_and_extract/`.  These logs can be replayed via `find_and_extract.sh rollback …` to restore individual files or an entire run (details in `docs/FIND_AND_EXTRACT_TOOL.md`).

## Guest File Writes Without Python Payloads
- `_write_guest_file` now writes data through a sequential `bash` pipeline instead of Python payload uploads. The flow is:
  1. Confirm the target directory exists (`test -d`).
  2. Create a temporary file in the same directory (fallback: `/tmp`) using `mktemp`.
  3. Use a `bash -lc` heredoc to place the normalized content into the temp file.
  4. Preserve permissions and ownership from the original file when it exists (`stat -c '%a %u %g'`), otherwise default to `644` and the executor's UID/GID.
  5. Atomically replace the original file with `mv tmp target` and remove the temp file on failure.
- This approach satisfies the requirement to rely on standard shell utilities (no Python inside the guest, no base64 payload) while still handling multi-line content safely.

## Firewalld Zone Schema and Synchronization
- Source-side collection now records the complete firewalld state (`interfaces`, `sources`, `ports`, `rich_rules`) into `FirewalldZonePlan` objects. Validation is performed by `FirewalldZoneSchemaValidator` against `schemas/firewalld_zone_schema.json`, so malformed zones are skipped with a debug log instead of aborting the run.
- The validator and dataclass reside in `firewalld_schema.py`, which can be imported directly or via `_load_local_module` when packaging constraints exist.
- `_sync_firewalld_configuration_to_prd` accepts an optional list of `FirewalldZonePlan` objects. When provided:
  - Interfaces: The planned set is treated as authoritative-even an empty list triggers removal of stale assignments, eliminating the previous "all NICs drift into public" issue.
  - Sources, ports, and rich rules: The code transforms staging values to PRD equivalents and enforces an exact match by removing extras and adding missing entries.
  - Every modifying action ensures a zone backup (timestamped copy under `/etc/firewalld/zones/`) before calling `firewall-cmd --permanent ...`. Changes are batched per zone and followed by a single `firewall-cmd --reload` when necessary.
- When no source plan is available, the function still attempts best-effort PRD transformations but leaves unattested settings untouched.

## Operational Notes
- Backups: `/etc/hosts`, `/etc/profile`, firewalld zone XMLs, NTP configs, and yum repo files are all guarded with timestamped backups before modification. Review these files if you need a manual rollback.
- Transformation utilities: `transform_text_to_prd` and related helpers remain the first line of defense for STG->PRD substitutions; the schema-driven firewalld sync complements them by handling structural data rather than plain text.
- Extensibility: When new guest configuration tasks require detailed command descriptions or structured data capture, reuse the patterns above to stay consistent with the execution summary and validation expectations.

For additional implementation details refer to `cloneAndVmotion.py`, `guest_commands.py`, and `firewalld_schema.py` in the project root.
